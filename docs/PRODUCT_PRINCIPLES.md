# 产品原则与范围

本文记录 SFL 的产品边界、新需求判断标准及取舍依据。日常开发指令见 [AGENTS.md](../AGENTS.md)。

## 核心产品原则

**SFL 是本地图片—代码知识库客户端，通过本地界面和外部调用接口管理、检索与复用图片及其代码；具体研究任务的组织、执行与持续管理，交给拥有项目上下文的宿主 Agent。**

科学图、参考图、模板代码及其关联、说明和来源是知识库的核心管理对象。
SFL 不以接管完整科研绘图工作流或成为科研项目管理系统为目标。
用户在使用 SFL 的过程中遇到的需求，不自动成为 SFL 应承担的功能。
判断功能归属时，优先考虑管理对象、独有价值和长期责任，而不是是否与绘图有关或实现是否简单。

## 本地客户端与外部入口

2026-09-15 用户明确归纳的产品定义以本节为准；此前将 SFL 整体定位为 MCP App，或要求
两端都采用同一种桌面 UI 技术的描述不再作为实施依据。

- **本地客户端**：macOS 使用原生 SwiftUI；Windows 与 Linux 使用 Node 服务器提供本地 Web 页面，
  通过随包携带的 Node 运行时启动。macOS 包也携带后端所需的私有 Node 运行时。
- **共享后端**：复用现有 TypeScript/Node 服务、全局 Library、Provider、图片—代码关联及
  精确选择和写入契约。本地界面不另建权威图库或另写一套业务规则。
- **简单本地应用**：本地 App 不内置 AI、模型调用或 Agent 任务编排，直接调用共享图库
  业务层；仅外部工具通过 MCP 接入，不新增 App 内部的 MCP Client 或代理链路。
- **外部调用**：通过 MCP 和一个核心 `SKILL.md` 供外部 CLI/Desktop 调用，返回候选图片
  列表、精确资产身份和后续使用接口。
- **简化 MCP App**：面向支持 MCP App 的宿主提供候选浏览、简要预览、选择和交接。
  完整的知识库管理界面由本地客户端承接。

这是确定的产品与平台方向。已实现能力和客户端待实现项分别见
[Agent 接入方案](AGENT_INTEGRATION.md) 与 [本地客户端架构](LOCAL_CLIENT.md)。

## 外部 Agent 接入原则

SFL 向外部 Agent 工具开放本地图片—代码知识库能力。接入对象包括 zcode、
WorkBuddy、Claude Desktop、Codex Desktop、Wisp Science 等；这些名称表示目标宿主，
不代表所有版本均已完成兼容性验收。

- 以一个核心 `SKILL.md` 维护宿主调用指导，详细说明按需加载，避免为每个宿主维护一套业务流程。
- 图库检索、候选图片获取、精确预览、选择和材料化应能通过宿主可调用接口完成。
  宿主可用自己的图片展示、选择控件或对话承接交互。
- MCP 是标准接入方式，简化 MCP App 是可选交互入口。新增核心能力不应仅能通过 App 私有状态或组件专用返回值访问。
- Skill 说明如何使用服务；是否加载指导、如何展示图片、如何执行项目任务由宿主负责。
  服务端验证资产身份和写入契约，不能以 Skill 文本代替这些验证。
- 按宿主实际具备的工具、资源读取和图片展示能力验收，不根据产品名称推定兼容。

第一阶段已实现核心 Skill、指导读取、候选图片及普通工具分页。开发状态、
后续 Desktop 设计与宿主验收要求见 [Agent 接入方案](AGENT_INTEGRATION.md)。

## SFL 应承担的职责

- 管理可跨项目复用的图片—代码知识资产，包括科学图、参考图、模板代码、图片与代码的关联，以及说明、元数据、来源、许可和固定版本。
- 提供本地知识库客户端，以及供外部 CLI/Desktop 调用的 MCP、核心 Skill 和简化 MCP App。
- 提供图库浏览、检索、预览、选择、导入、发布和材料化等能力，以及与这些能力直接相关的完整性检查。
- 改善用户发现、理解和使用图库的体验，包括选择反馈、需求表达示例、用户手册和模板使用说明。
- 向宿主 Agent 提供明确的资产、工具契约和使用指导，便于其在用户项目中完成后续工作。

图库自身的持久化、资产身份、版本、来源记录和发布包管理属于上述职责，不应与研究项目管理混淆。

## 不应扩展为 SFL 原生职责的能力

除非用户明确要求调整产品边界，否则不要新增以下能力，也不要将其承诺为 SFL 保证完成的行为：

- 保存实验室或用户的绘图偏好，并跨会话自动应用、协调覆盖关系或保证输出符合规范。
- 默认接管用户项目的目录组织，强制一图一文件夹，持续维护实际数据、脚本、参数和输出的对应关系，或提供项目级投稿归档与打包管理。
- 管理具体论文的主图/子图身份、编号、别名、修订和计划状态，或同步改名、重排后的项目文件与引用。
- 编排上游分析、执行用户绘图代码，或承担完整研究任务的生命周期管理。

这些需求应优先由宿主 Agent 结合项目约定和执行环境实现。SFL 可以提供必要的模板信息与 Skill 指导；
提供指导不等于接管项目状态，也不应据此宣称插件已实现自动执行、长期记忆或持续一致性保证。
已有相关指导或兼容能力不构成继续扩大产品范围的理由，也无需仅因本原则进行破坏性删除。

## 新需求的归属判断

在新增功能前，先判断：

1. **管理对象**：管理的是可复用的图库资产，还是某次研究任务的过程、偏好和产物状态？后者默认归宿主 Agent。
2. **独有价值**：是否依赖 SFL 掌握的图库资源或契约，或显著改善图库本身的可靠性与使用体验？仅将 Agent 的通用文件操作包装成专属接口，不足以成为新增理由。
3. **可控责任**：SFL 能否在自身控制范围内验证所承诺的结果？若长期正确性依赖宿主执行、用户后续编辑或整个项目的同步维护，不应由图库独自承诺。
4. **长期成本**：评估的不只是新增按钮、配置文件或接口的开发量，还包括状态迁移、覆盖规则、失败恢复及持续一致性维护责任。

对混合需求，只实现属于图库职责的部分，并清楚说明与宿主的交接边界。
普通功能请求不自动视为调整产品定位的授权；越界需求应说明归属，并优先采用宿主 Agent 或项目约定承接。
不要借“轻量配置”“辅助功能”或“完善体验”引入实质上的项目管理子系统。
