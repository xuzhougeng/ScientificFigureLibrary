# SFL 优化记录（2026-10）

本文记录 2026-10-17 至 2026-10-18 对 Scientific Figure Library 0.9.1 做的一轮整体分析：发现了哪些问题、依据是什么、维护者做了什么决定，以及每一项当前的状态。**"已完成"指代码已经合并或在待合并的 PR 中；"设计"和"暂缓"表示还没有实现。** 所有数字都来自实测，测量方法写在对应条目里。

## 1. 分析框架

从用户的基本诉求出发——"一张类似这样的图，用我自己的数据画出来"——SFL 的价值取决于三件事：

| 要素 | 含义 | 分析时的状态 |
|---|---|---|
| 找得到 | 快速找到合适的模板，不漏检 | 薄弱：关键词打分，没有浏览入口，中文需求句经常零命中 |
| 信得过 | 拿到的正是看到的那个精确版本 | 很强：精确 selector、一次性凭据、plan/apply 摘要、重放、过期检查 |
| 用得上 | 步骤少、token 成本低 | 偏重：headless 路径 6 次调用，62 个工具约 72 KB 的定义 |

根本原因归纳为四点：

- **A 检索**：排序依赖人工维护的关键词词典，没有利用宿主 Agent 的语义理解能力。
- **B 使用路径**：为发布设计的安全仪式，被同样严格地套在了"使用模板"的读取路径上。
- **C 复杂度**：交付目标（6 个宿主插件、多种安装包）多于团队规模能维护的量。
- **D 上下文漂移**：过时的规格文档和路径会误导开发时使用的 Agent。

## 4. 已讨论、尚未实施的设计

### 4.1 语义卡

- 语义卡是**从模板自身元数据计算出来的视图**（图类型、科学问题、输入数据、视觉特征、不适用于、关键词），不单独维护文件。
- OFM 的语义字段由 Open Figure PR 工具根据 Local 元数据自动生成；Local 录入时由 Agent 填写；只有 FigureYa（第三方上游）需要在 SFL 仓库中维护补充文件。
- **决定**：本轮不全量生产语义卡。是否投入，取决于更难的第二轮测试（全量约 438 个模板、30 条含近义变体的查询、每组 3 次）。
- 待定：新模板必填字段的强度（`scientificQuestion` 等）；OFM 中缺少 `scientificQuestion` 的 36 个模块是否补全；生成 module.yml 时是否保留 `visualProfile`。

### 4.2 打包内容与网络

- **决定**：不考虑离线使用（没有网络就无法使用 LLM，也就用不了插件）；用不了 GitHub 时由用户配置代理，统一走 GitHub + 0.9.1 的代理设置；线上 feed 的传输方式保持现状。
- **决定**：插件包只保留目录元数据（几百 KB），作为首次启动和访问失败时的兜底，并在发版时刷新到最新；去掉打包的全部预览图（以 Wisp 0.8.1 为例，解压后 OFM 图片 22.7 MB、FigureYa 缩略图 3.7 MB），改为与 npm 包一致的按需下载（`preview-downloads.json`）。
- 依据：OFM 的源码归档本来就不打包，材料化必须联网；#59 之后，挑选可以只依靠文本目录完成。
- 状态：设计，未实施。实施时需更新打包脚本、包体积门禁与发布说明。
